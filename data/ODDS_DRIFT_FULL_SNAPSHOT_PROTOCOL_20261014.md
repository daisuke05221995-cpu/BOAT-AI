# 全120通りオッズの継続収集・昇格判定プロトコル

登録日: 2026-10-14。研究収集のみ。Android・Model A・BUY/SKIP閾値・資金配分・凍結済み実運用会計は変更しない。

## 目的と測定対象

同じレースの同じ組番について、締切前の表示オッズと締切後の確定表示オッズを組番ごとに対応させる。当選組番で標本を選ばない。現金の払戻倍率、締切直前の表示倍率、締切後の確定表示倍率を別変数として保存する。同着・返還時にこれらが一致するとは限らない。

## 発見済みの取得先

- 締切前全120通り: `https://race.boatcast.jp/txt/{jcd}/bc_smt_od3_{YYYYMMDD}_{jcd}_{rno}.txt`
- 確定全120通り: `https://race.boatcast.jp/txt/{jcd}/bc_kakutei_od3_{YYYYMMDD}_{jcd}_{rno}.txt`
- 独立の列対応確認: `https://www.boatrace.jp/owpc/pc/race/odds3t?hd={YYYYMMDD}&jcd={jcd}&rno={rno}`
- 払戻・同着・返還確認: 公式結果ページ。払戻CSVの1組番だけで同着の全配当を再現しない。

2026-07〜10月の少数レースで確定配信先を確認した。保持期間・全開催の可用性・通常時の更新時刻は保証されない。今回の研究スナップショットは時刻とSHA-256を固定して保存する。

## 収集方法

1. 開催・出走情報から対象を列挙し、結果を見る前に収集対象リストを固定する。原則全レース、負荷制約があれば開催場・日・レース番号で事前に無作為抽出する。AIがBUYとしたレースだけに絞らない。
2. 締切予定12.5分前から約1分周期で取得する。3・5・7・9・12分前それぞれに最も近いスナップショットを、目標±30秒の条件内で一意に選ぶ。同じ生データを複数の時点に複製しない。近い取得がなければ欠測とする。
3. 締切予定90秒前〜直後は可能な範囲で15秒周期とし、最後の有効な締切前表と、発売終了を観測した時刻を別に保存する。締切延長・中止・通信失敗はステータスとして残す。締切予定時刻を実際の投票締切時刻と呼ばない。
4. 確定表は締切後に30〜60秒周期で取得し、少なくとも20分までは再試行する。遅延レースは当日の回収処理で継続する。全120通りがそろい、別時点の取得で安定を確認できた表を確定候補とする。最初の取得と安定確認の両方を残す。
5. 1つのレースに対する120列を1リクエストで取得する。サーバーの応答・制限に従い、初期設定は最大2リクエスト開始/秒・同時8件以下。429・5xx・タイムアウトはバックオフし、失敗・取得なし・未発売・返還を区別する。

## 保存スキーマ

各スナップショットに以下を必須保存する。

| 分類 | 必須項目 |
| --- | --- |
| 識別 | schemaVersion, raceCode, dateJst, venue, raceNumber, captureRunId |
| 時刻 | scheduledCloseAt, observedSaleEndAt（不明ならnull）, requestStartedAt, responseCompletedAt, sourceUpdatedAt（配信元が明示しない場合null）, HTTP Date, timezone |
| 出所 | sourceUrl, HTTP status, sourceKind（pre / lastPre / finalQuote）, parserVersion, sourceAppVersion（アプリ由来のみ）, liveOddsSource |
| 生データ | rawBody, sha256, responseHeaders, parsedCombinationCount |
| オッズ | 120組番の値・原文・表示精度・発売/返還状態。null/0を正の倍率で埋めない |
| 結果 | 全当選組番の払戻、返還艇、同着、中止、結果の確認時刻 |

レコードキーは `(raceCode, sourceKind, responseCompletedAt, sha256)`。集計キーは `(raceCode, preCaptureId, finalCaptureId, combination)`。タイムゾーンは保存時UTCのISO8601、集計時Asia/Tokyo。個々のHTTP応答完了時刻から残り時間を計算する。処理開始時刻を全レースに流用しない。配信元更新時刻が得られなければ、画面/ファイルの内部更新遅れが不明であることをフラグに残す。

## 品質管理と除外

- 組番は1〜6から異なる3艇を選ぶ正確な120通り。欠落・重複・異なるレース・非数値・未発売を記録する。通常6艇の正の120通りと、返還/欠場による縮小市場を分ける。
- パース列は明示ラベル付き公式HTMLと独立に照合する。導入時は24場×複数日で検証し、その後は変更検知・日次抽出照合を行う。
- 1000倍以上の整数表示は0.1倍精度の払戻と厳密一致を要求しない。原文と精度区間を保存する。同着の払戻と最終表示オッズの差をパース誤りと決めつけない。
- 当選組番が一致しないレースだけを黙って除外しない。全通りパネルに残してフラグ付き主解析と、理由を明示した感度解析を報告する。
- 分析分母は事前対象レース。成功レースだけで収集完備率を計算しない。時刻帯・場・順位・月ごとに欠測率を出す。

## 暫定係数を置き換える最低条件

これは今回新規提案する研究上の昇格条件であり、既存の360 audited BUY判定を変更する条件ではない。

- 60日以上・通常6艇の一意レース2,400以上。24場を対象に、少なくとも20場で各30レース以上。
- 人気順位6区分 × 残り時間5区分（0〜4、4〜6、6〜8、8〜10、10〜15分）の各セルに、一意レース300以上、30日以上、12場以上。90組番/レースを90レースと数えない。
- 各時間帯の全120通りペア完備率95%以上。欠測理由が把握でき、欠測レースと成功レースの事前オッズ/場/時刻の分布差を説明できる。
- 構造・表示精度の既知例外を除いた独立HTML照合の一致率99.9%以上。未解決の組番ずれや混在した配信時刻がない。
- 最初のデータで単純な順位×時間補正を事前固定する。最後の連続14日・500レース以上を一度だけ開く未使用検証期間にする。必要なセル数に届かなければ継続収集する。
- 評価は日/レース単位で扱い、raw prior・現行prior・候補priorの対数倍率誤差、中央値誤差、過大推定率、予測区間の被覆率を比較する。各セルの中央値係数の95%日クラスタCI幅は0.08以下を目安とする。
- オッズ誤差の改善が確認できても、購入ROI改善とは呼ばない。Model A・BUY/SKIP・資金配分を変えず、将来の実運用エビデンスは `sourceAppVersion` と `liveOddsSource` で分離し、既存凍結ルールで評価する。

標本不足のセル、測れなかった実締切・配信遅延に対して係数を外挿しない。歴史的な全通りパネルは設計と偏りの検証に使い、正確な応答時刻を持つ前向きデータで補正の運用妥当性を判断する。
